# ShareTrip Contract Service

Микросервис на Go для договорных условий и проверки доступности услуг компаний платформы ShareTrip.

## Ответственность сервиса

Contract Service отвечает **только** за:

- хранение договоров компаний;
- статусы и сроки действия договоров;
- список услуг, разрешённых договором;
- ответ на бизнес-вопрос: *разрешена ли компании конкретная услуга по действующему договору*.

### Что сервис не делает

| Область                           | Кто отвечает                                    |
|-----------------------------------|-------------------------------------------------|
| Пользователи и роли               | Keycloak / слой авторизации вызывающего сервиса |
| Создание и жизненный цикл поездок | ShareTrip                                       |
| Уведомления и каналы доставки     | Notification Service                            |
| Оплата и счета                    | вне области                                     |
| Юридические файлы договора        | вне области                                     |
| История изменений договора        | вне области (учебное ограничение)               |

Сервис **не** проверяет, кто залогинен, и **не** проверяет роли. Вызывающий сервис (например ShareTrip) уже авторизован
и передаёт `companyId` и код услуги.

## Структура репозитория

```
api/contract.yaml   — внешний OpenAPI-контракт
migrations/         — SQL-миграции схемы хранения
cmd/contract/       — точка входа (заготовка)
internal/           — внутренний код (заготовка под будущую реализацию)
go.mod              — Go-модуль
README.md           — ответственность, бизнес-правило, проверка границ
```

Реализация бизнес-логики на Go на этом этапе **не требуется** — важно правильно определить границу сервиса.

## Внешний API

Описание: [`api/contract.yaml`](api/contract.yaml).

| Действие                                      | Метод  | URL                                      |
|-----------------------------------------------|--------|------------------------------------------|
| Создать договор                               | `POST` | `/contracts`                             |
| Получить договор по id                        | `GET`  | `/contracts/{contractId}`                |
| Получить активный договор компании            | `GET`  | `/companies/{companyId}/active-contract` |
| Изменить статус договора                      | `POST` | `/contracts/{contractId}/status-changes` |
| Заменить список услуг договора                | `PUT`  | `/contracts/{contractId}/services`       |
| Проверить доступность услуги                  | `POST` | `/contracts/service-availability-checks` |
| Проверить доступность услуги создания поездки | `GET`  | `/contracts/can_create_trip/{clientId}`  |

Проверка доступности — отдельный бизнес-метод. ShareTrip вызывает его перед созданием поездки и не обращается к БД
Contract Service напрямую.

## Схема хранения (PostgreSQL)

Две области (см. `migrations/`):

1. **Договоры** (`contracts`) — `id`, `company_id`, `status`, `starts_at`, `ends_at`.
2. **Услуги договора** (`contract_services`) — список услуг (`service_code`) и признак доступности (`is_available`).

Ограничения и индексы:

- PK на обеих таблицах; FK `contract_services.contract_id → contracts.id`;
- статусы через ENUM `contract_status`: `draft`, `active`, `suspended`, `terminated`;
- у компании только один договор со статусом `active` (partial unique index);
- услуга не дублируется в рамках одного договора (`UNIQUE (contract_id, service_code)`);
- индексы по `company_id`, `status`, `(company_id, status)`, `contract_id`, `service_code`.

## Бизнес-правило: проверка доступности услуги

Метод `POST /v1/service-availability-checks` отвечает на вопрос:

> Может ли компания с идентификатором `companyId` использовать услугу с кодом `serviceCode` прямо сейчас?

### Вход

- `companyId` — идентификатор компании;
- `serviceCode` — код услуги (например `trip.create`, `trip.share`).

### Алгоритм

1. Найти договор компании со статусом `active`.
    - Если нет → **отказ**, `NO_ACTIVE_CONTRACT`.
2. Убедиться, что статус не `suspended` / `terminated`.
    - `suspended` → `CONTRACT_SUSPENDED`;
    - `terminated` → `CONTRACT_TERMINATED`.
3. Сравнить `now` с периодом договора:
    - `now < starts_at` → `CONTRACT_NOT_STARTED`;
    - `ends_at` задан и `now > ends_at` → `CONTRACT_EXPIRED`.
4. Найти услугу с кодом `serviceCode` в договоре.
    - Нет записи → `SERVICE_NOT_IN_CONTRACT`.
5. Проверить `is_available`.
    - `false` → `SERVICE_DISABLED`.
6. Все проверки пройдены → `allowed: true`.

### Результат

| Исход             | Ответ API                                 |
|-------------------|-------------------------------------------|
| Услуга доступна   | `{ "allowed": true, ... }`                |
| Услуга недоступна | `{ "allowed": false, "reason": "<код>" }` |

### Коды причин отказа

| Код                       | Смысл                  |
|---------------------------|------------------------|
| `NO_ACTIVE_CONTRACT`      | Нет активного договора |
| `CONTRACT_SUSPENDED`      | Договор приостановлен  |
| `CONTRACT_TERMINATED`     | Договор расторгнут     |
| `CONTRACT_NOT_STARTED`    | Срок ещё не начался    |
| `CONTRACT_EXPIRED`        | Срок истёк             |
| `SERVICE_NOT_IN_CONTRACT` | Услуги нет в договоре  |
| `SERVICE_DISABLED`        | Услуга отключена       |

ShareTrip по `allowed` и `reason` решает, создавать поездку или вернуть ошибку. Contract Service поездки не создаёт.

## Проверка границ сервиса

| Вопрос                                                                            | Ответ                                                                                     |
|-----------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------|
| Может ли ShareTrip создать поездку без прямого доступа к базе Contract Service?   | **Да.** ShareTrip вызывает HTTP API проверки доступности.                                 |
| Может ли Contract Service изменить внутреннюю схему хранения, не ломая ShareTrip? | **Да.** ShareTrip зависит только от OpenAPI-контракта.                                    |
| Есть ли логика поездок?                                                           | **Нет.** Нет сущностей trip — только коды услуг вроде `trip.create`.                      |
| Есть ли логика уведомлений?                                                       | **Нет.**                                                                                  |
| Есть ли логика авторизации пользователя?                                          | **Нет.** Нет пользователей, ролей и сессий.                                               |
| Понятно ли из API, какие решения принимает сервис?                                | **Да.** Операции — бизнес-действия, не CRUD над строками.                                 |
| Не превратился ли сервис в CRUD над `contracts`?                                  | **Нет.** Центр — проверка доступности услуги с учётом статуса, сроков и включённых услуг. |
